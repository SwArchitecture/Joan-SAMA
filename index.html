SAMA — Static Archtecture Memory Analyzer

Analyze Flash and RAM allocation in a linked TriCore firmware ELF on Windows. SAMA reads the firmware without running it or connecting to a target device.

1. What you need

  • Windows executable: use Joan-SAMA.exe for the interactive console or Joan-SAMA-CLI.exe for automation. You only need the executable for the mode you use. No source code or development environment is needed to run it.
  • Firmware ELF: the final linked TriCore ELF32 executable for your firmware, not an object file or a .hex or .bin image.
  • Project YAML: the configuration for your firmware project. It defines analysis settings such as memory limits and module grouping.
  • Chip YAML: a SAMA-compatible memory map for the exact device and variant. Use the configuration approved for your firmware and linker layout.

The executable does not replace the input files. If you received only the executable and this guide, obtain the ELF and compatible YAML files from your firmware or integration team before running an analysis.

Which file answers which question? The ELF says where the linker placed the firmware. The chip YAML says which physical memories those addresses map to and how large they are. The project YAML says how to group and check usage. The JSON records what SAMA found.

2. Interactive console: Joan-SAMA.exe

  1. Double-click Joan-SAMA.exe.
  2. Enter the firmware ELF path and press Enter.
  3. Enter the chip YAML path and press Enter. On the first visit to this prompt, leave it blank to use the project YAML's chip setting. If a chip file is already selected, type :default to clear the override.
  4. Enter the project YAML path and press Enter.
  5. Enter the output JSON path, or press Enter to save mem_report.json beside the ELF. Choose a writable folder that already exists.
  6. Review the paths and press Enter to analyze. If the output already exists, type yes only if you want to replace it.

At the input prompts, use :back to return one step or :quit to exit. Once the JSON is saved, press Enter to close or type :new to run another analysis.

3. Command-line interface: Joan-SAMA-CLI.exe

Use this executable for repeatable runs or automation. Open PowerShell in the folder containing the CLI executable. Supply the firmware and configuration paths in the command; the CLI does not ask for them interactively.

Quick start: chip path already set in Project YAML

.\Joan-SAMA-CLI.exe ".\firmware.elf" --project ".\project.yaml"
$LASTEXITCODE

Specify the chip and output explicitly

.\Joan-SAMA-CLI.exe ".\firmware.elf" --project ".\project.yaml" --chip ".\chip.yaml" --out ".\mem_report.json"
$LASTEXITCODE

Replace the example paths with your files. Relative paths typed on the command line are resolved from the current PowerShell folder. Quote any path containing spaces.

ArgumentMeaning
firmware.elfRequired positional path to the linked firmware ELF.
--projectRequired path to the project YAML.
--chipOverrides the project YAML's chip path. Omit if the project YAML references the correct chip file.
-o / --outOutput JSON path. Defaults to mem_report.json in the current folder. Create the parent folder first.
--help / -hPrints command syntax when used by itself.

For scripts: the CLI replaces an existing output without asking. Capture $LASTEXITCODE right after the command and use the exit-code table to distinguish a policy failure (JSON written) from an operational failure.

4. Project YAML: how to analyze the firmware

YAML is a plain-text configuration format. Save the files as UTF-8. Write settings as key: value, indent nested settings with spaces (not tabs), and use - for list entries. Use unquoted numbers for addresses, sizes and ratios; use true or false for switches. Addresses and byte counts can use decimal or 0x hexadecimal notation. Quote core IDs and use single quotes around regular expressions to preserve backslashes.

This example shows an analysis policy, not production limits. Keep the memory settings and naming rules aligned with your firmware.

schema: tc4x-project/1
project: ExampleFirmware
chip: chip.yaml
options:
  sota: linear
  enable_cache_as_ram: false
  module_attribution: section
thresholds:
  default:
    warn: 0.85
    error: 0.95
policy:
  fail_on: error
  top_symbols: 30
SettingMeaning
schema, projectFormat label and project display name. The project name appears in the JSON.
chipPath to the chip YAML. A relative path is resolved from the project YAML's folder. An explicitly selected chip file takes precedence; when one is supplied, this key is not required.
options.sotalinear uses the normal Flash map. A or B selects the active software-over-the-air (SOTA) Flash slot for analysis. Use A/B only when both the linked firmware and chip YAML match that layout.
options.enable_cache_as_ramAdds configured scratchpad extensions only when the hardware and linker use cache storage as RAM. It does not turn caching on or off.
options.module_attributionsection groups whole sections by section name. symbol groups eligible functions and objects by symbol name; use an ELF with its static symbol table. This changes module estimates, not physical region totals.
options.exclude_regionsList of chip region names to exclude from capacity totals. Allocations in an excluded run region can still be reported as errors.
core_rulesMaps core IDs to section-name patterns. The first matching rule selects the core for a core-local address.
modulesOrdered list of rules, each with a name, a regular-expression pattern and optional budget.flash / budget.ram in bytes. First match wins; unmatched entries go to OTHER.
reservedList of allocations not already in the ELF. Each uses name, region, size in bytes and optional offset from the region's primary base. Without an offset, the reservation is placed at the end of the region.
thresholdsUsage ratios apply at or above the limit: 0.85 means 85%, not 0.85%. Optional min_free warns when free bytes fall below the configured count. Overrides apply per field in order: default, type, group, then region. Use null to disable an individual limit.
policyfail_on: error fails on errors; warn also fails on warnings; never keeps findings but does not fail on them. unmapped, overlap and module_budget accept error, warn or ignore. top_symbols caps the largest-symbol list; 0 disables it.

5. Chip YAML: which addresses belong to which memory

Use a complete, validated memory map for the exact silicon variant and linker configuration. The excerpt below shows a single RAM region to explain the format. It is not a complete chip file for a firmware analysis.

schema: tc4x-chip/1
device: TC499
variant: PE
address_view_types:
  DLMU:
    primary: non_cached
    alias: cached
regions:
  - name: CPU0_DLMU
    type: ram
    group: DLMU
    core: '0'
    start: 0xB0000000
    size: 0x80000
    alias: [0x90000000]
SettingMeaning
schema, device, family, variantDescriptive labels for the YAML format and silicon. Device and variant appear in the report.
regionsRequired nonempty list of physical memories. Each entry has a unique name, type (flash or ram), primary start address and nonzero size in bytes. group classifies the memory; core labels its owning core where applicable.
regions[].aliasOptional list of alternate base addresses for the same bytes. Each window is the same size as the primary range; do not enter an alias as a separate physical region.
address_view_typesLabels primary and alias windows by region group: cached, non_cached, alias or unknown. These labels describe the address windows, not the current CPU cache state.
cores, local_windowscores provides core IDs and global scratchpad base addresses. For a core-local range, local_windows defines its name, base, size and target (a base-address field such as dspr or pspr). Cache-as-RAM additionally uses dspr_size, pspr_size, dcache_ext and pcache_ext in the core configuration.
sota_layoutFor A/B layouts, banks.A and banks.B list the physical Flash banks in each slot. active and inactive define their start windows and alias windows. The project YAML selects which slot is active for this analysis.

Why two addresses do not mean twice the RAM: In this example, 0x90000020 and 0xB0000020 refer to the same byte, 32 bytes from the start of the region. SAMA reports the linked address as-is and normalizes it to the primary window for accounting. Capacity is still 512 KiB. Changing either YAML file does not relink the ELF or reconfigure the device.

6. JSON output: what SAMA found

JSON is a structured text report generated by the executable, not an input configuration. Open it in a text editor or use a JSON parser for automation. Read checks to see what needs attention, then use regions and sections to identify where. The analyzer writes JSON only. To create HTML and Excel, pass that JSON to the separate Joan-SAMA-Report.exe.

Example: read a memory region

This excerpt shows selected fields only. Sizes and addresses are JSON numbers in decimal. pct is a fraction despite its name: 0.75 means 75% used. In this example, 128 KiB remains free.

{
  "schema_version": 1,
  "regions": [
    {
      "name": "CPU0_DLMU",
      "start": 2952790016,
      "size": 524288,
      "used": 393216,
      "free": 131072,
      "pct": 0.75
    }
  ],
  "checks": [],
  "exit_code": 0
}
JSON fieldMeaning
schema_versionReport format version. The format documented here is version 1. Check it before parsing reports in automation.
metadataInput paths, project and device details, and effective settings. Review this section before sharing a report; paths can reveal local directory names.
regionsOne row per reported physical memory region. start is the primary base, size is capacity, used is accounted usage, and free is remaining capacity, in bytes. The sample start value, 2952790016, is 0xB0000000. status and the effective limits show how usage was evaluated. address_views lists access windows, not extra memory.
sectionsAllocated ELF sections. vma is the linked run address; lma is the inferred load address. run_region shows the run mapping; load_region is populated for a separately counted load placement. vma_view and lma_view describe the windows; canonical_vma and canonical_lma give normalized addresses or null if not resolved. A load address alone does not prove that startup code copies the section.
placementsEntries used to account for memory: section data, separately counted initialization data and explicit reservations. Use region, addr, size and kind to inspect where bytes were counted.
modulesFlash and RAM usage estimates grouped by project rules, with budgets where configured. Use regions, not the sum of the module estimates, for physical capacity decisions.
checksFindings, each with severity, check (category), item (affected entry) and detail. An empty list means no findings were reported under the current policy.
top_symbolsLargest available ELF functions and data objects, with their addresses, sizes and locations. This list may be empty in a stripped ELF or if disabled.
exit_codePolicy result recorded in a successfully written report. It may be 0, 1 or 2. Process exit code 3 indicates an operational failure, not a valid new report.

Reading missing values: null means unavailable or unset, not zero. [] means a list has no entries.

CLI exit codes

CLI exit codeMeaning
0Analysis completed and met the configured policy. Non-blocking findings may still be present.
1JSON saved. Warnings caused the configured policy to fail.
2JSON saved. Errors caused the configured policy to fail.
3The run failed. Read the console error and do not treat an existing output file as a result of this run.

SAMA reports static allocation from the ELF and YAML files. It does not measure runtime memory use, peak stack usage, or the target's actual cache state.

7. Troubleshooting

  • Chip YAML not found: check the project YAML's chip reference or supply the chip file explicitly.
  • Many sections are unmapped: verify that the chip variant and project memory settings match the linker layout used for the ELF.
  • Cannot write JSON: choose a writable folder that already exists and an output path distinct from all inputs.
  • Still blocked: email joan.software@outlook.com with the executable name and exact console error. Redact sensitive paths and share firmware or configuration files only through an approved channel.
